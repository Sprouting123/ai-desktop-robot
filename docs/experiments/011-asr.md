# 实验 011：本地中文语音识别（ASR）

- 状态：**已验收（识别部分）**（2026-11-08 用户确认：录音中能听到的内容就是“一二三”，ASR 识别正确；用户在“一二三”之前还说了几个字，但没有被录进 WAV。录音起始截断属于实验 010 的采集流程问题，见 5.2、6、9）
- 日期：2026-11-08（Asia/Shanghai）
- 前置实验：[010 INMP441 麦克风采集与录音](010-microphone.md)、[009 MAX98357A 音频输出](009-audio-output.md)

## 1. 目标与范围

实验 011-1 的目标是把实验 010 已经生成的 3 秒 WAV 录音，在本机识别为中文
文字，验证“录音 → 语音识别 → 文本”链路。本阶段只在 Ubuntu 上运行 ASR：

- 不修改 ESP32 固件，不烧录；
- 不调用任何付费 API；
- 不把录音上传到第三方语音识别服务；
- 使用独立 Python 虚拟环境，不影响 PlatformIO 的 `.venv/`；
- 所有模型、虚拟环境、录音与日志都在本机 `work/`（被 Git 忽略）。

识别文字是否准确由用户最终确认。模型能够运行、输出非空文本，都不等于识别正确。

## 3. 模型选型与下载

### 3.1 候选方案

| 方案 | 中文能力 | CPU 可行性 | 结论 |
| --- | --- | --- | --- |
| FunASR Paraformer-large（本项目） | 专为中文普通话音视频/会议场景训练 | 官方支持 CPU；本机实测 RTF≈0.03 | **采用** |
| FunASR SeACo-Paraformer | 在 Paraformer 上增加热词定制 | 同为 CPU 可运行 | 暂不采用，模型更大；后续做命令词热词时可评估 |
| Whisper / faster-whisper | 多语种，中文可用 | CPU 可运行，通常慢于 Paraformer | 本阶段未实测；作为备选 |
| Vosk / sherpa-onnx | 中文小模型，体积小 | 轻量 | 精度与中文体验未验证；作为嵌入式方向的备选 |

本阶段选择 FunASR 的 Paraformer-large：免费、可完全本地运行、中文普通话
表现成熟，且 CPU 推理速度足以支撑后续交互实验。

### 3.2 选定模型与下载前说明

- 模型 ID：`iic/speech_paraformer-large_asr_nat-zh-cn-16k-common-vocab8404-pytorch`
- 来源：ModelScope（魔搭）模型库，模型提供方 `iic`
- 许可证：Apache License 2.0
- 下载前披露的大小：约 889 MB
- 实际下载：10 个文件，2026-11-08 实测约 30 秒、23–30 MB/s
- 磁盘占用：

| 文件 | 字节 | 说明 |
| --- | --- | --- |
| `model.pt` | 880,502,012（839.7 MiB） | 模型权重 |
| `seg_dict` | 8,287,834（7.9 MiB） | 分词词典 |
| 整个模型目录 | — | 848 MiB |

**关于 `paraformer-zh` 别名：** FunASR 1.4.24 把 `paraformer-zh` 映射到
SeACo-Paraformer（约 999 MB），而不是本实验选定的原始 Paraformer-large。
为与下载前的 889 MB 说明一致、避免隐式切换到更大的模型，本实验在脚本中显式
固定上面的完整模型 ID，不使用别名。

### 3.3 缓存位置

`scripts/asr_local.py` 在导入 `funasr`/`modelscope` 之前设置
`MODELSCOPE_CACHE`，默认指向项目内 `work/models`。该目录被 `.gitignore`
忽略，不会提交；删除后下次运行会重新下载。首次运行后再次识别会复用本地权重，
不会重新传输模型文件；从日志看 ModelScope 仍会做一次快速的缓存/文件列表检查，
因此“离线可用”尚未单独验证。无论是否联网，音频只在本地读取，不会上传。

## 4. 识别脚本

新增 `scripts/asr_local.py`，只依赖 `work/asr-venv`：

```bash
env -u PYTHONPATH work/asr-venv/bin/python scripts/asr_local.py work/mic-20261108-181323.wav
```

- 先用标准库 `wave` 校验输入：必须是 PCM、16000 Hz、16 bit、单声道、至少一帧；
  不满足时输出 `ERR: ...` 并以非零状态退出。
- 保留原始 16 kHz 单声道输入，不做重采样或格式转换。
- 模型加载与推理分开计时；输出模型 ID、设备、缓存目录、音频格式与时长、
  模型加载时间、推理耗时、RTF（推理耗时/音频时长）、CPU user/sys 时间与平均
  使用核数、进程峰值 RSS、识别文本。
- 模型下载、加载或识别失败时打印 `ERR: <原因>`，退出码为 1。
- 可选参数：`--model`、`--cache-dir`、`--device`（默认 `cpu`）。

## 5. 测试过程与结果

### 5.1 输入音频

`work/` 中现有 6 个 3 秒录音，均为 16 kHz / 16 bit / 单声道 / 48,000 帧
/ 96,044 字节：

| 文件 | 说明 |
| --- | --- |
| `mic-20261108-181323.wav` | 实验 010 最终验收样本（CRC `ac9af219`） |
| `mic-20261108-181039.wav` | 另一段 3 秒录音 |
| `mic-20261108-174341.wav` | 早期 3 秒录音 |
| `mic-20261108-180309.wav` | 同一段录音的原始版本 |
| `mic-20261108-180309-boost.wav` | 同一段录音的增益版本 |
| `mic-20261108-180309-agc.wav` | 同一段录音的 AGC 版本 |

对最终样本做 10 ms 窗能量分析：样本峰值 0.69998（归一化后），以窗口最大 RMS
的 10% 为门限，有效段约为 0.66–0.98 s（0.32 s）与 1.07–1.21 s（0.14 s），
合计约 0.46 s；其余为静音/低能量。这与实验 010 记录的“有效语音约 0.6 秒”
量级一致（具体数值随门限不同），说明这段音频内容很短，识别结果只能在短句
范围内比较。

### 5.2 识别结果

用同一个模型依次识别 6 个文件：

| 文件 | 识别文本 |
| --- | --- |
| `mic-20261108-181323.wav` | `一二三` |
| `mic-20261108-181039.wav` | `啊` |
| `mic-20261108-174341.wav` | `right is` |
| `mic-20261108-180309.wav` | `the the the知嗯` |
| `mic-20261108-180309-boost.wav` | `the都the知嗯` |
| `mic-20261108-180309-agc.wav` | `the the不知嗯` |

最终样本的输出为“一二三”。该段有效语音约 0.46 秒，分成两组，与三个短音节
的节奏相符。

**用户确认（2026-11-08）**：录音里实际只有“一二三”这几个字；在“一二三”之前
用户还说了几个字，但**没有录进 WAV**。因此：

- ASR 对已经录制到的内容识别正确，未发现误识别、漏字或噪声导致的错误；
- “少字”的原因是录音开始得太晚，不是 ASR 漏识，属于录音流程问题；
- 这次验收只覆盖“对已录制音频的识别”，不能证明麦克风录音能完整保留一段话。

其余 5 个文件输出“啊”“right is”“the the the知嗯”等无意义内容，说明在没有
有效语音或语音很弱时，模型仍可能给出看似正常的文本，不能把“有输出”当作
识别成功。

### 5.3 已知内容对照

为在不依赖麦克风录音的情况下检查模型本身的准确性，把仓库中已知内容的
`assets/audio/hello_zh.raw`（Edge TTS 生成的“你好，我是你的 AI 桌宠！”，
16 kHz/16 bit/单声道，2.463 s）临时转成 `work/hello_zh_known.wav` 后识别：

- 实际内容：你好，我是你的 AI 桌宠！
- 识别文本：`你好我是你的ai捉宠`

对照结果：文字内容基本正确，仅“桌”被识别为同音字“捉”，大小写与标点未输出
（本阶段未接标点模型）。即 10 个有效字符中 9 个正确，说明模型与加载链路本身
工作正常；这不能替代对麦克风录音内容的确认。

### 5.4 性能

| 指标 | 首次运行 | 缓存后运行 |
| --- | --- | --- |
| 模型加载 | 33.00 s（含约 30 s 下载） | 2.65–2.78 s |
| 推理耗时（3 秒音频） | 0.10 s | 0.10–0.11 s |
| RTF | 0.032 | 0.032–0.035 |
| CPU 时间（推理） | 未单独记录 | user 0.37–0.40 s，sys≈0 |
| 推理平均占用 | 未单独记录 | 约 3.8–3.9 核 |
| 进程峰值 RSS | 2,251.8 MB | 2,254.5–2,270.4 MB |

在 i5-12400F 上，3 秒音频的推理约 0.1 秒，远快于实时；主要开销是一次性
加载约 2.3 GB 的模型与运行时。模型常驻后（后续实验若做常驻进程）单次识别
的增量成本很低。

## 6. 结果分析

- 最终样本被识别为“一二三”，且用户确认录音中实际能听到的正是“一二三”；
  对该段已录内容，识别结果正确。用户在“一二三”之前还说了几个字，但没有被
  录进 WAV，因此这次测试暴露的是录音起始截断，而不是 ASR 漏识。
- 截断原因：原脚本提示用户“倒计时数到 3 就开始说话”，而 `mic record` 要等
  倒计时结束后才发送，固件还会丢弃启动后的 0.5 秒；用户从“3”开始说的话，
  前约 2.5 秒落在录音窗口之外，3 秒录音只保留了结尾。
- 有效语音仅约 0.46 秒，信息量不足以评估连续语音、长句、数字和专有名词表现。
- 对静音/弱语音文件，模型会输出英文词或语气词等无意义文本，说明后续链路必须
  加能量门限或 VAD（语音活动检测），不能对每段录音无条件调用 ASR。
- 已知内容 TTS 对照出现一个同音字错误（桌 → 捉），且没有标点；这是本模型在
  无热词、无标点模型条件下的正常表现，不代表麦克风录音的识别质量。

## 8. 问题与处理

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| torchaudio 与 torch 版本不匹配 | `torchaudio.load()` 抛出 `ImportError`，要求安装 `torchcodec` | FunASR 的 `load_audio_text_image_video()` 会捕获异常并回退到 `soundfile`；已用目标 WAV 验证回退读取成功（48,000 点、float32、峰值 0.69998）。当前不改动依赖版本 |
| ROS `PYTHONPATH` 干扰 | pip 解析时出现 ROS 包告警 | 统一用 `env -u PYTHONPATH` 运行，不修改系统 ROS |
| `paraformer-zh` 别名指向 SeACo | 别名对应模型约 999 MB，与下载前说明的 889 MB 不一致 | 显式使用原始 Paraformer-large 的完整模型 ID |
| 静音/弱语音产生无意义文本 | 多个文件输出 `the the the知嗯`、`right is` 等 | 记录为限制；下一步加能量门限或 VAD，不把非空输出当作识别成功 |
| 录音起始截断 | 用户先说几个字、WAV 只从“一二三”开始；前约 2.5 秒未被录到 | 2026-11-08 修改 `scripts/capture_mic_wav.py`：倒计时只用于准备，发送 `mic record` 并等待 0.6 秒（越过固件丢弃的 0.5 秒启动瞬态）后显示 `>>> SPEAK NOW`，提示用户此时才开始说话。该改动只涉及主机提示时序，尚未用新流程重录验证 |

## 9. 下一步建议

1. **按新提示重录并核对完整句子**：`capture_mic_wav.py` 已改为倒计时只准备、
   录音启动 0.6 秒后提示 `>>> SPEAK NOW`；请从看到该提示时开始说，并说明
   实际说了什么，作为下一轮对照。该新流程尚未在硬件上验证。
2. **重录一段内容更完整的 3 秒语音**：例如“你好，我是小机器人”，并在录制时
   记录实际文本。当前 3 秒录音有效语音仅约 0.46 秒，且开头被截断，不足以
   评估连续语音。
3. **增加 5–10 秒录音与 VAD**：固件侧延长录音或分段传输；主机侧接入
   `fsmn-vad`（FunASR 自带）先检测语音段，再送 Paraformer，避免静音段被
   模型“脑补”为文字。对完整句子的识别，5–10 秒比固定 3 秒更合适。
4. **加标点模型**：接入 `ct-punc` 可改善可读性；本阶段输出无标点是预期行为。
5. **面向命令词优化**：桌宠的“开心/难过/停止”等固定命令可评估 SeACo 的
   热词功能或小模型命令词识别，降低延迟与资源占用。
6. **再考虑端侧或云端**：本阶段 ASR 在 Ubuntu 主机上运行，ESP32 只负责录音与
   传输；后续需明确“设备直连云端 ASR”还是“局域网主机识别”，并重新评估隐私、
   延迟与离线可用性。
