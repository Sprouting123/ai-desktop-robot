# 实验 010：INMP441 I²S 数字麦克风采集

- 状态：**第二阶段已验收**（2026-11-08 用户试听 3 秒 WAV，报告“能听清说话内容”；三环境构建、烧录校验与 1187 项回归通过）。第一阶段已验收（2026-11-08 用户讲话观察：安静 peak 1% → 说话 peak 6%；固件读取右声道）
- 日期：2026-11-08（Asia/Shanghai）
- 前置实验：[009 MAX98357A 音频输出](009-audio-output.md)、[008 Wi-Fi 控制](008-wifi-control.md)

## 1. 目标

第一阶段：在不影响扬声器、OLED、舵机、Wi-Fi 与 HTTP 的前提下，用 INMP441
采集麦克风数据，并通过串口查看近期峰值、RMS 与采样计数。

1. 新建独立的 `microphone_engine` 模块。
2. 使用 Arduino-ESP32 2.0.17 自带的 ESP-IDF legacy I²S 驱动，优先使用
   `I2S_NUM_1` 的 RX 模式。
3. 标准 I²S，16kHz、32bit 接收槽；正确处理 INMP441 的 24bit 有符号采样与
   左声道（实测该模块数据在右声道，最终改为右声道且数据格式不变，见 6.3）。
4. DMA 分块读取，主循环不等待。
5. 新增 `mic status`、`mic start`、`mic level`、`mic stop`。
6. 上电默认不采集、不保存、不上传；未连接或全零数据不虚报成功。

第二阶段：3 秒 RAM/PSRAM 录音、可靠传输与完整性校验、Ubuntu 生成
16kHz/16bit/单声道 WAV 并试听。本阶段不接入在线识别、云端 AI 或任何付费 API，
不上传音频。第一阶段已于 2026-11-08 通过用户讲话观察，第二阶段随后实施，见第 7、8 节。

## 3. 设计

### 3.1 I²S 参数

| 项目 | 值 |
| --- | --- |
| 端口 | `I2S_NUM_1`，仅 RX，主模式 |
| 引脚 | BCLK GPIO16、WS GPIO17、DIN GPIO18、无 MCLK |
| 格式 | 标准 I²S（Philips） |
| 采样率 | 16 kHz |
| 槽宽 | 32 bit（`I2S_BITS_PER_SAMPLE_32BIT`） |
| 声道 | `I2S_CHANNEL_FMT_ONLY_RIGHT` + `I2S_CHANNEL_MONO`（实测该模块数据在右槽） |
| DMA | 4 × 256 帧（16 kHz 下每块 16ms，约 64ms 余量） |

- INMP441 输出 24bit 二进制补码，在 32bit 槽内左对齐，低 8 位补零。固件读取
  32bit 字后算术右移 8 位还原 24bit 有符号值；满量程为 2²³ = 8,388,608。
- 扬声器仍使用 `I2S_NUM_0` TX 与 GPIO6/7/15，两个端口、两组引脚互不重叠。

### 3.2 按需初始化

- 上电只调用 `begin()` 打印配置，**不安装 RX 驱动**：不输出时钟、不分配 DMA、
  不采集；`mic status` 显示 `state=idle ready=0`。
- 首次 `mic start` 才安装驱动并开始 RX；`mic stop` 调用 `i2s_stop()` 停止
  外设但保留驱动，便于快速重启。
- `update()` 每轮最多调用一次 `i2s_read(..., 0)`；没有数据立即返回，不阻塞。
- 驱动安装失败时 `mic start` 返回 `ERR mic_not_ready`，`mic status` 显示
  `state=error` 与 `last_error`。

### 3.3 近期统计与静音判断

- 每个 256 帧块记录峰值、平方和与“是否全零”。
- 最近 32 块（约 0.5 秒）组成滑动窗口，`mic level` 输出窗口内的峰值、RMS、
  采样数与块数；停止采集后保留最后一个窗口供查看。
- `signal` 判定：
  - `idle`：未采集；
  - `no_data`：窗口内还没有样本；
  - `zero`：窗口内所有块全部为 0；
  - `ok`：窗口内存在非零样本。
- `mic level` 的 `peak`/`rms` 是 24bit 原始值，另给出相对满量程的整数百分比。
- 注意：非零不代表数据可信。INMP441 未接时数据线悬空可能读到随机噪声，
  固件无法区分“真实环境声”和“悬空噪声”；只有用户对着麦克风讲话并看到
  数值随声音变化，才构成第一阶段实物验收。

### 3.4 串口命令

| 命令 | 行为 |
| --- | --- |
| `mic status` | `MIC state=... ready=... port=1 bclk=16 ws=17 din=18 sample_rate_hz=16000 ... frames=... blocks=... reads=... timeouts=... zero_blocks=... errors=... last_error=...` |
| `mic start` | 开始采集；已运行时回复 `restarted=1` 并重置窗口与计数 |
| `mic level` | `MIC_LEVEL state=... signal=... window_frames=... window_blocks=... peak=... rms=... peak_pct=... rms_pct=... total_frames=... zero_blocks=...` |
| `mic stop` | 停止采集；保留驱动与最后一个窗口，帧计数冻结 |

非法子命令或多余参数返回 `ERR mic_usage; use help`。所有命令都不会保存音频、
写 Flash 或发起网络请求。

- 保持舵机 60–120° 软件限位与所有既有命令不变。

- 启动日志包含 `MIC_CONFIG installed=0 port=1 bclk=16 ws=17 din=18 ...`，

## 7. 第二阶段：3 秒录音与 WAV 导出

### 7.1 目标与验收标准

1. 在 RAM/PSRAM 中录制固定 3.0 秒、16kHz、16bit、单声道音频
   （48,000 帧、96,000 字节），不写 Flash。
2. 通过串口把原始 PCM 完整传回电脑，带偏移量、长度与 CRC-32 校验；
   丢行、乱序或校验不符必须能被发现，不能静默生成错误 WAV。
3. Ubuntu 端生成可直接播放的 16kHz/16bit/单声道 WAV。
4. 不接入在线识别、云端 AI 或付费 API，不上传音频；开发期间外部 5V 保持断开。
5. 验收：固件与脚本自动检查通过，且用户实际试听 WAV 后确认能听清说话内容。

### 7.2 固件设计

- 新增录音状态 `record=idle|recording|ready`，与采集状态 `state=` 分开报告。
- 首次 `mic record` 时分配 96,000 字节缓冲：优先
  `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`，失败时退回内部堆，并打印
  `MIC_RECORD_ALLOC bytes=96000 psram=1`（或 `psram=0`）。缓冲只分配一次，
  多次录音复用；复位后录音丢失。
- 录音开始时使能 I²S RX，**先丢弃前 8,000 帧（0.5 秒）的启动瞬态**，再采集
  48,000 帧。瞬态是这块板开始输出时钟时的饱和/衰减伪影，诊断过程见 8.3。
- 24bit 采样右移 16 位得到 16bit PCM，按小端写入缓冲。
- 采满 48,000 帧后计算整段 CRC-32（多项式 0xEDB88320，初值与结果异或
  0xFFFFFFFF，与 Python `zlib.crc32` 相同），调用 `i2s_stop()` 停止 RX，
  状态转为 `ready`，打印：
  `MIC_RECORD_DONE frames=48000 bytes=96000 sample_rate_hz=16000 sample_format=s16le channels=1 crc32=xxxxxxxx`。
- `mic dump` 只在 `ready` 时启动，按 48 字节一行、每行 96 个十六进制字符输出，
  共 2,000 行；每轮 `loop()` 最多发一行，且只在 `Serial.availableForWrite()`
  足够时发送，不阻塞 OLED、动作、Wi-Fi/HTTP 与麦克风驱动。DMA 停止后仍可
  继续传输（`update()` 先推进 dump，再判断是否采集）。
- 状态与错误路径：
  - `mic status` 增加 `record=`、`record_frames=`、`record_bytes=`、`record_crc=`；
  - 未录音时 `mic dump` → `ERR mic_no_recording`；
  - 录音中 `mic start`、`mic record`、`mic dump` → `ERR mic_recording`；
  - dump 未结束时再次 `mic start`/`mic record`/`mic dump` → `ERR mic_dump_busy`；
  - 录音中 `mic stop` 中止并丢弃本次录音（`record=idle`、0 帧），已完成但未
    导出的录音在 `mic stop` 后保留为 `ready`；
  - 再次 `mic record` 会覆盖上一段录音；
  - 分配失败返回 `ERR mic_record_failed`。
- 上电仍只打印 `MIC_CONFIG`，不采集、不录音、不发声；录音与传输都不写 Flash、
  不发起网络请求。

### 7.3 串口传输协议

```
PCM_BEGIN bytes=96000 frames=48000 sample_rate_hz=16000 format=s16le channels=1 crc32=<8 hex> line_bytes=48
PCM 000000 <96 个十六进制字符，48 字节，小端 16bit>
PCM 000030 <...>
...
PCM 0176d0 <...>            (最后一行偏移 0x0176D0 = 95,952)
PCM_END lines=2000 bytes=96000 crc32=<8 hex>
```

- 每行偏移是字节偏移，步长 48，覆盖 0–95,999；2,000 行 × 48 字节 = 96,000 字节。
- `crc32` 在 `PCM_BEGIN`、`MIC_RECORD_DONE` 与 `PCM_END` 中必须一致。
- 115200 8N1 下 192,000 个十六进制字符加行头约需 20 秒；实际耗时取决于串口
  与主机读取速度。
- 传输是“每轮一行”的非阻塞实现，但持续占用串口带宽；传输期间输入其他命令的
  行为未做专项验证，不列为支持用法。

### 7.4 主机脚本 `scripts/capture_mic_wav.py`

- 先核对设备身份（VID 0x1A86、PID 0x55D3、序列号 `5D4D001473`），独占打开
  串口，不拉 DTR/RTS。
- 默认 5 秒倒计时，只用于准备；发送 `mic record` 并等待 0.6 秒（越过固件丢弃的
  0.5 秒启动瞬态）后显示 `>>> SPEAK NOW`，提示“从现在开始大声说话，一直说到
  recording finished”。`--delay` 可改倒计时，`--out` 指定输出路径。
  （2026-11-08 实验 011 复测发现旧的“数到 3 就开始说”会截掉开头约 2.5 秒，
  已改为当前提示。第二次录音 `mic-20261108-190250.wav` 确认开头不再丢失，但
  3 秒窗口在说话中途结束，结尾仍会被截断。）
- 发送 `mic record`，等待 `MIC_RECORD_DONE`（8 秒超时），再发送 `mic dump`
  （60 秒超时）；校验 `PCM_BEGIN`、每行偏移连续、总长度 96,000 字节、
  `PCM_END` 与主机 `zlib.crc32` 一致，任何一项不符即报错退出，不写 WAV。
- 处理链：int16 解包 → 记录原始峰值 → 一阶 30Hz 高通去除 INMP441 的直流偏置
  与慢漂移（不改变语音频段）→ 峰值归一化到满量程 70%，增益上限 64× →
  限幅后写入 `work/mic-YYYYmmdd-HHMMSS.wav`（16kHz、16bit、单声道、3.000 秒）。
- `--no-normalize` 保留原始电平；`--gain N` 使用固定线性增益。脚本打印 CRC 校验
  结果、原始峰值、去直流后峰值与百分比、实际增益。
- 音频只保存在本机 `work/`（被 Git 忽略），不上传、不进入仓库。

  `MIC_RECORD_DONE` 的长度与格式；`record=ready` 及帧/字节/CRC 与完成日志一致；
  `mic stop` 保留录音；dump 的头部、2,000 行连续偏移、96,000 字节、主机

  被拒；`help` 包含 `mic record | mic dump`。
- 原始日志（本机，Git 忽略）：`work/regression-010-phase2d.log`。回归只能证明
  固件、串口与脚本逻辑，不能证明声音内容。

### 8.3 诊断过程（2026-11-08）

1. **启动瞬态**：首次录音的前约 0.4–0.5 秒是满幅饱和并快速衰减的伪影。
   对比实验：复位后直接录音时存在；“预启动 2 秒再录”时消失。固件因此增加
   `kSettleFrames = 8000`，每次 `i2s_start` 后先丢弃 0.5 秒再采集。
2. **直流偏置**：原始波形整体偏离零点（数个百分点满量程）并缓慢漂移。
   主机端加入 30Hz 一阶高通，语音频段基本不受影响。
3. **1kHz 声音测试**：对着麦克风播放 1kHz 声音后录音，频谱在 1000Hz 处出现
   明显峰值（幅度约 816，相邻频点 2–5），证明采集链路能正确还原频率；
   不是在保存噪声。
4. **实时电平**：用 `mic level` 每 0.5 秒采样 12 秒，安静时窗口峰值约 4–5%，
   在 5–10cm 处大声说“啊——”时依次出现 53%、24%、14%、12%。此前的
   “只有噪声没人声”录音判断与说话太轻、距离太远或起录太晚有关，不是麦克风
   故障——同一接线与固件在靠近、大声、按提示起录后可以得到可懂语音。
5. **提示调整**：录音提示曾改为“倒计时到 3 就开始说话”，让说话落在 3 秒窗口
   中部，而不是只在末尾一两秒。2026-11-08 实验 011 中用户反馈“一二三之前还说了
   几个字但没录到”：按该提示，用户从“3”开始说时距 `mic record` 真正开始还有
   约 2 秒，再加 0.5 秒启动瞬态，开头会被截掉。因此再次调整为主机在录音启动
   0.6 秒后提示 `>>> SPEAK NOW`，用户从提示出现时开始说。2026-11-08 第二次录音
   （`mic-20261108-190250.wav`）确认开头已捕获，但 3 秒窗口在句子中间结束，
   结尾仍被截断；固定 3 秒无法容纳整句，需延长录音。

### 8.5 限制与未验证项

- 只验证了固定 3 秒、单次触发、16kHz/16bit/单声道；没有连续录音、流式传输、
  触发阈值或掉电保存。录音在 RAM/PSRAM 中，复位即丢失。3 秒不足以容纳
  “开始测试，这是一个AI测试”这类整句，第二次录音在说话中途被截断。
- 最终验收样本中有效语音仅约 0.6 秒；更长的连续讲话、不同距离与背景噪声下
  的可懂度未测试。
- 串口 dump 的 20 秒是基准估算，实测耗时未记录；dump 期间其他命令的响应未
  专项验证。
- 麦克风灵敏度、噪声底、频响、失真、长期稳定性以及 3V3 供电余量未测量。
- 实验 010 本身未接入语音识别、云端 AI 或任何付费 API，也没有音频上传链路；
  后续[实验 011](011-asr.md) 已在 Ubuntu 主机侧使用本地 FunASR 完成识别验证。
